# 聊天网关

[English](gateways.md) | 简体中文

Joy 支持四个聊天平台。各平台的接法不同是因为平台本身就不同；本页收集
真实世界的细节。所有网关都与本地 `joy app-server` 通信，会话 id 从平台
身份派生。

## 启动网关

```sh
just gateway-telegram / gateway-discord / gateway-wechat / gateway-lark
```

## Telegram

Telegram 网关要一个 bot token（找 @BotFather 要）：

```bash
TELEGRAM_BOT_TOKEN=123:abc TELEGRAM_ALLOW=@你的用户名 just gateway-telegram
```

`TELEGRAM_ALLOW` 是允许名单（数字 id 或 `@用户名`，逗号分隔）。**不设就是谁都能用**，
而花的是你的模型额度 —— 临时自己试可以，放出去的 bot 一定要设。

Discord 网关要一个 bot token：去 <https://discord.com/developers/applications>
建应用 → Bot → Reset Token。**还得在同一个页面上把 `Message Content Intent` 打开** ——
Discord 默认不给 bot 消息正文，不打开的话连接会被直接掐掉（报的是 4013）。
两步都做完，再把 bot 邀进服务器，然后：

```bash
DISCORD_BOT_TOKEN=… DISCORD_ALLOW=@你的登录名 just gateway-discord
```

`DISCORD_ALLOW` 跟 Telegram 那条是一回事：数字 id 或 `@登录名`，逗号分隔，不设就是谁都能用。

四个平台的接法各不相同，因为平台各不相同：Telegram 那边是**长轮询**（网关自己推
offset，断了没拿到的还会再来），Discord 那边是**一条 WebSocket**，得按它的规矩心跳、
IDENTIFY、断了重连。所以 Discord 的适配器只做了「重新连上」，**没做 RESUME** —— 断的
那几秒里说的话就是丢了。要补上得记住 `session_id` 和 `resume_gateway_url`，那会是整条
链上唯一需要持久状态的地方。

还有一条使用上的差别：服务器频道里**不 @ 它就不接话**。Discord 的 bot 能看见频道里
每一条消息，而一个对每句话都插嘴的 bot 第二天就会被踢出服务器；私聊里没这个问题
（那儿本来就只有你们俩），不必 @。

**说明：这条路还没连过真的 Discord。** 它要一个真 bot token，本地和 CI 都拿不到 ——
`scripts/smoke-gateway.sh` 证明的是「网关 → app-server」那条链（会话 id 从平台身份
派生、SSE 归拢成完整答复）。适配器自己的规矩 —— 心跳与序号、重连要重新握手、@ 的
判定、白名单、切长消息、429 重试、发不出去不能把整个网关带走 —— 单测都钉住了，但
「真的能连上 Discord」是第一个跑它的人验证的。

## 微信

微信是四家里最不一样的一个：它**没有能连出去的路** —— 不给长轮询，也不给 WebSocket，
只能当个 HTTP 服务器等着被推。所以这是唯一需要「公网可达 + 一个地址」的网关，本地跑
得先配内网穿透，而且微信只认 80 和 443 两个端口（TLS 建议交给前面的反向代理，别在这
个进程里做）。

要的东西在公众平台的「设置与开发 → 基本配置 → 服务器配置」：Token、AppID、AppSecret、
EncodingAESKey，回调 URL 填 `http://你的域名/wechat`。

```bash
WECHAT_TOKEN=… WECHAT_APP_ID=wx… WECHAT_APP_SECRET=… just gateway-wechat
```

**这一家最关键的一条规矩是 5 秒。** 微信把消息推给你之后只等 5 秒，超了就重试（一共
三次），三次都没回就把用户那句话丢掉。而 Joy 跑一轮 —— 尤其带工具调用的那几轮 ——
远超 5 秒。所以主流路径不是「被动回复」，而是：

1. 收到消息，**先把答复的事交给 Joy，同时掐一个 4 秒的表**
2. 4 秒内答得完、而且一段装得下 → 就地被动回复，一次 API 都不调
3. 没答完 → **立刻回一个 `success`** 把微信打发走，然后拿客服消息把答复推回去

那个 4 秒是留给网络和微信那头的余量。这个顺序不是风格问题：反过来做，用户会收到三份
一模一样的回答（微信重试了三次），所以适配器按 `MsgId` 记了最近 200 条，重试的请求
直接跳过。

**两个门槛得说在前面，它们是微信那边的，绕不过去：**

- **客服接口只有认证过的公众号能调。** 个人未认证的订阅号会一直报 `48001`。那种号就
  只剩上面第 2 条 —— 4 秒内答得完的才回得了话，慢的都没有下文。
- 客服消息有额度：用户发来一条消息，换来**48 小时内 5 条**。所以长回答被切成几条是
  要花额度的，这也是为什么「能被动回复就别走客服」值得单独写一段逻辑。

加解密三种模式都认（明文 / 兼容 / 安全）—— 入站正文先规约成明文 XML，之后所有逻辑
只认一种形状，不必到处分情况。加密按下配的 `WECHAT_AES_KEY`，不配就是明文模式；
**微信那边选了什么模式，这边就得配什么**，配错的表现是「验证 URL 失败」。
`packages/gateway/src/wechat-crypto.ts` 单独一个文件、全是纯函数，因为它是最不能
「差不多就行」的一段：差一个字节微信就是静默不理你。它拿**官方文档里那条密文**当
测试向量 —— 那一条同时钉住了密钥推导、CBC 与 IV、32 字节补齐、明文布局四件事。

**说明：这条路还没连过真的微信。** 它要一个真公众号 + 一个公网地址，本地和 CI 都拿不
到。但除了「微信服务器真的推过来」这最后一步，其余都能在本机验：加解密对上了官方文档
里那条密文；`scripts/smoke-gateway.sh` 里有一段真的起 HTTP 服务器、真的验签、真的把
回包的 XML 吐出来（会话 id 也是从 openid 派生、服务端当场认下的）；单测钉住了三种模式、
4 秒竞速、`MsgId` 去重、白名单、切长消息、客服消息被拒不能把网关带走 —— 起的也是真的
HTTP 服务器，打桩的只有微信那两个 API 地址。剩下最后一步是第一个跑它的人验证的。

## 飞书

飞书又是另一种：它给**长连接**，所以不用公网地址、不用内网穿透 —— 但方向反过来，
连接建起来之后**要我们先开口**，服务端才认这根线是活的。也正因为它把「收到了」和
「答完了」拆成了两件事，这儿没有微信那个 5 秒问题：**ACK 先拍回去，再慢慢想**。

要的东西在开发者后台的「凭证与基础信息」：App ID、App Secret。

```bash
LARK_APP_ID=cli_… LARK_APP_SECRET=… LARK_ALLOW=ou_… just gateway-lark
```

`LARK_ALLOW` 填的是 **open_id**（`ou_…` 那串），**不是 App ID** —— 这是最容易填错的
一处；跟另外三家一样，不设就是谁都能用。连国际版 Lark 加 `LARK_DOMAIN=lark`。

**后台那三件事缺一件，表现都是「连上了、永远没反应」，而且连报错都没有：**

1. 开启**机器人能力**
2. 订阅 `im.message.receive_v1`
3. 订阅方式选**长连接**，不是「将事件发送至开发者服务器」

第三件最阴：选了另一个，长连接照样建得起来，事件却一条都不过来，而日志上干干净净。
`bin-lark.ts` 起来时会把这三条一并列出来。

帧是飞书私有的 `pbbp2`，`lark-proto.ts` 里手写了个 protobuf 编解码，不引运行时。
有个不显眼但要命的地方：`logId` 是**超过 2^53 的整数**，而 ACK 要原封不动回填 ——
所以它用 BigInt 存。用 `number` 会在第 16 位丢精度，表现是**偶发的不应答**，最难查的
那种。大消息会被切成分片，凑齐了才处理（没凑齐就当没收到，而不是把半截 JSON 拿去解，
那只会得到一句「事件不是 JSON」）。群里跟 Discord 那条规矩一样：@ 别人就不插嘴。

**说明：这条路还没连过真的飞书。** 它要一个已发布的企业应用，本地和 CI 都拿不到。
`scripts/smoke-gateway.sh` 里那一段打桩的只有远端那两个地址（假 socket + 假 HTTP），
**中间全是真跑的**：真编解码（自己编的帧自己解不开会当场炸）、真 ACK 回显（含那个超
2^53 的 `logId`）、真去重与分片、真 app-server —— 会话 id 也是从 openid 派生、服务端
当场认下的。适配器自己的规矩单测都钉住了，剩下最后一步是第一个跑它的人验证的。
